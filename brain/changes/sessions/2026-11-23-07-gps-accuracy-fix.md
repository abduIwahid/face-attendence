# Session 07 — GPS accuracy fix (best-of-several sampling + accuracy-aware decision)

- **Date:** 2026-11-23
- **Goal / request:** Bug fix from Wadi's real phone test (2026-11-23 ~21:08 PKT): sitting in the **exact spot** where he had set the class location from the teacher dashboard, /verify told him he was ~160–170 m away. Cause: indoor GPS drift — a single-shot browser geolocation reading indoors can be off by 100–200 m (the first fix is often a Wi-Fi/cell position). The Phase 2 semantics (single-shot fix → raw haversine vs radius, 50 m accuracy cap) made the core feature fail in the normal classroom case.
- **What was done:**
  - **New shared sampling routine — `lib/geolocation.ts`.** `sampleBestPosition()`: `watchPosition` with high accuracy for up to ~10 s, keeps the reading with the smallest reported accuracy, stops early when a fix reaches ≤ 20 m. Resolves `{ ok | denied | unavailable }`; transient watch errors are not final (a later update may still deliver before the deadline). Used by both location consumers so the class point and the student fix are measured the same way.
  - **/verify page.** "Share my location" now samples: the button shows "Improving location accuracy…" while sampling, `LocationStatus` gained a `sampling` state ("Improving location accuracy… Best so far: ±X m"), and the best-so-far fix drives the live distance preview. The submit gate now keys off the new cap via `GPS_ACCURACY_CAP_METERS` imported from `lib/verify.ts` (single source of truth). The "ok" state judges "looks too far" on the **effective** distance and, when the raw distance exceeds the radius but the effective distance passes, says so ("within your GPS accuracy, so it can still count") — what the student sees matches what the server will decide.
  - **Teacher setter (`ClassLocationSettings`).** "Use my current location" uses the same sampling routine; the button shows the live best accuracy while sampling ("Improving location accuracy… ±X m").
  - **Server decision — `lib/verify.ts` (ADR-009).** New pure helper `effectiveDistanceMeters(distance, accuracy) = max(0, distance − accuracy)`; the TOO_FAR gate now tests the effective distance against the radius. `GPS_ACCURACY_CAP_METERS` raised 50 → **250** (a fix worse than ±250 m is meaningless; GPS_INACCURATE still writes no attendance row). Rejection ordering otherwise identical; outcomes still carry the **raw** distance and the route still stores raw distance + accuracy — only the decision changed.
  - **`lib/geo.ts`.** `isGpsAccurate` default cap aligned to 250 m with an ADR-009 comment.
  - **Copy alignment.** The GPS_INACCURATE API message now says "a fix worse than ±250 m cannot be used"; the verify page's helper text explains sampling; SECURITY.md, API_SPEC.md, GLOSSARY.md (new "Effective distance" entry), ETHICS_PRIVACY.md and JUDGE_QA.md updated from the 50 m wording to the ADR-009 semantics.
  - **Tests — 25/25 passing** (`npm test`): the 50 m-cap tests updated to the 250 m cap (250 passes the gate, 260 → GPS_INACCURATE, GPS ordering test now uses 300 m accuracy); new cases — `effectiveDistanceMeters` (subtract + floor at 0), **Wadi's case (raw 165 m / ±160 m accuracy / 100 m radius → PRESENT, outcome still carries raw 165)**, raw 300 m / ±170 m → TOO_FAR (effective 130), effective distance exactly at the radius boundary → PRESENT. The old raw-boundary tests pin accuracy 0 so raw == effective.
  - **Build + deploy + live-verify.** `npm run build` passes; lint clean. Deployed to Vercel production via the REST digest-upload route (same as session 06): deployment `dpl_FHyWXqqjbcu15WehgbunNSH9Thnd`, READY. Live checks on https://face-attendance-ai.vercel.app: `/`, `/login`, `/register`, `/verify` → 200; POST /api/verify with a valid-shape payload for an unregistered roll → 404 NOT_REGISTERED (designed path, no row written, no fake students created); the served /verify chunk contains the new "Improving location accuracy…" string — the sampling code is in the production bundle.
- **Decisions + reasoning:**
  - **ADR-009** — GPS: best-of-several sampling + accuracy-aware radius decision; cap 250 m. Indoor drift is the normal classroom case; the phone's own accuracy figure is the honest trust measure for the raw distance. Raw values stay logged for teacher audit. Trade-off accepted for v1 (RISKS.md R-11): a just-outside student with a terrible fix can pass on effective distance.
  - **Docs:** ADR-009 amends ADR-004's cap; RISKS.md R-02 mitigation rewritten and R-11 added for the accepted trade-off.
- **Problems + fixes:**
  - The old "distance exactly at radius" tests silently changed meaning under the effective-distance rule (default test accuracy 12 m made 101 m raw into 89 m effective) — they now pin `gpsAccuracyMeters: 0` so raw == effective and the boundary intent is preserved.
